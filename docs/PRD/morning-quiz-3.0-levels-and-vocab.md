## 1. 为什么做

学校给这套系统定了新名字：**「词汇以及雅思 / O-Level 各等级英语训练」**。

拿这个名字对照 2026-08-24 的现状，四个要素只兑现了一个半：

| 名字里的要素 | 现状 | 差距 |
|---|---|---|
| **词汇** | 有生词本 + 交卷后必经自测，32 人 519 词 | 是早测的附属品，没有独立入口、没有进度感；519 词里 **352 词从未复习过**；错题本 871 条 **销账 0 条** |
| **雅思** | 只有一档（剑桥真题原文） | 没有分层；且可用篇目**已全部服务过**，本周三场全是重复卷 |
| **O-Level 各等级** | 标准层在跑 | 基础层内容备好但**一个班没启用**；中间层 21 篇**没有任何等级在读** |
| **英语训练** | 主线是「每天一测、判分、出分」 | 训练成分（错题重练、间隔重复）是支线，且数据显示几乎没人走完 |

本次要把这四项全部补齐，并新增**雅思轻量层**，让「各等级」在雅思侧也成立。

## 2. 目标与非目标

### 目标

1. 英语等级从 3 个（实跑 2 个）扩到 **5 个，全部实跑**
2. 雅思侧补足内容，终结「重复卷」
3. 词汇从附属品升为**独立主线**：有入口、有进度、吞吐平衡
4. 错题重练打通，销账率从 0 起步
5. 出勤停用的收尾（面板 / 家长端 / 导出 / Seiue 流程）
6. 清掉历史欠账

### 非目标

- 不做真正的随机对照实验（样本 32 人、且教学公平性优先），度量方式见 §8
- 不重命名历史枚举值（见 §3.2 的决策与理由）
- 不改动第二作答窗的既有设计（2026-08-24 刚上线，见 [morning-quiz-2.0.md](./morning-quiz-2.0.md)）

## 3. 等级体系重构

### 3.1 目标形态：五级

| 对外显示名 | 枚举值 | 题库桶 | 规格 | 面向 |
|---|---|---|---|---|
| 雅思真题 | `ielts_authentic` | 剑桥真题 + `ielts_authored_2026` | 700–900 词，13–14 题 | 冲刺雅思的学生 |
| **雅思轻量**（新） | `ielts_light` | `ai_authored_ielts_light` | 250–350 词，6 题 + 词汇 | 想接触雅思题型但读不动长文的 |
| O-Level 标准 | `olevel` | `ai_authored_olevel_1128` 等 | 440–650 词，14 题 19 分 | O-Level 主力 |
| **O-Level 进阶**（复活） | `olevel_intermediate` | `ai_authored_olevel_1128_simplified` | 500–790 词，11 题 | 标准层吃力、基础层太浅的 |
| O-Level 基础 | `ielts_simplified` | `ai_authored_olevel_1128_basic` | 短文，5 题 + 词汇 | 最需要帮助的一档 |

### 3.2 关于命名的决策

**决策：不重命名历史枚举值，新增两个值，用显示名映射表统一对外呈现。**

理由：`ielts_simplified` 这个枚举位的语义已经变过一次（原「轻雅思」→ 2026-08-14 起是「O-Level 基础」）。数据库里挂着几个月的历史场次、答卷、考勤，重命名要改枚举 + 回填全部历史行，风险远大于收益。

代价是代码里的枚举名和 UI 名对不上。用一张**单一事实来源**的映射表兜住，禁止在别处硬编码中文名：

```ts
// apps/api/src/morning-quiz/level-registry.ts
export const LEVEL_REGISTRY = {
  ielts_authentic:      { label: '雅思真题',      bucket: 'ielts_authentic',  order: 1 },
  ielts_light:          { label: '雅思轻量',      bucket: 'ielts_light',      order: 2 },
  olevel:               { label: 'O-Level 标准',  bucket: 'olevel_standard',  order: 3 },
  olevel_intermediate:  { label: 'O-Level 进阶',  bucket: 'olevel_simplified',order: 4 },
  ielts_simplified:     { label: 'O-Level 基础',  bucket: 'olevel_basic',     order: 5 },
} as const;
```

### 3.3 雅思轻量层的内容规格

设计风格对齐 O-Level 基础层（短文 + 少量题 + 词汇），但保留雅思的**题型骨架**——学生练的是雅思的思维方式，不是换个皮的阅读理解。

| 项 | 规格 | 理由 |
|---|---|---|
| 文章长度 | 250–350 词 | 真题 700–900 太长，基础层学生读不完就放弃 |
| 题量 | 6 题 | 30 分钟场次，留 10 分钟给词汇 |
| 题型 | True/False/Not Given ×3 + 句子填空 ×3 | 这两类是雅思最核心、也最容易迁移到真题的 |
| 填空限制 | ONE WORD ONLY，答案是原文词 | 与真题规则一致，练的就是这个 |
| 配套词表 | 每篇 8 词 | 与基础层同一套推送机制 |
| 主题 | 科普 / 社会 / 环境，贴近真题选材 | 不用校园叙事——那是 O-Level 的路子 |

TFNG 的三条必须覆盖三种答案（各一条 TRUE / FALSE / NOT GIVEN），否则学生能靠猜同一个答案蒙分。

### 3.4 分层判定与去重

- picker 分发在 `pickPassageAndCreatePaper` / `pickOlevelPaperAndCreatePaper` 里按 `LEVEL_REGISTRY[level].bucket` 走
- **终身去重按层独立**（既有行为）：同一个班在 A 层做过的故事，不影响 B 层
- 雅思轻量与雅思真题**共用去重域**？→ **否**。两者内容完全不同（自撰短文 vs 剑桥原文），独立去重

## 5. 词汇模块升级

### 5.1 问题诊断（数据来自 2026-08-24 生产库）

| 指标 | 数值 | 含义 |
|---|---|---|
| 总词条 | 519 | — |
| 近 14 天新增 | 430 | 进得很快 |
| 近 14 天复习次数 | 156（18 人） | 出得慢 3 倍 |
| 从未复习（reps=0） | **352 / 519 = 68%** | 大部分词进来就沉底 |
| 错题总数 | 871 | — |
| 错题销账 | **0** | 重练这条路根本没走通 |

**根因**：收集无上限（答错自动采集）、复习有固定配额（每次 5–10 张）、且复习只有一个入口（交卷后那一次）。进出不平衡是结构性的，不是学生不努力。

### 5.2 改动

**(1) 独立入口 + 进度可视化**

学生自助页 `/my-vocab` 升级为词汇主页，顶部常驻三个数字：

- **已掌握** —— `reps > 0 且 state = Review 且 stability >= 21 天`
- **学习中** —— `reps > 0` 且未达掌握
- **待开始** —— `reps = 0`

外加**连续天数**（既有 `streakDays`）。目标是让学生第一眼看到「我学到哪了」，而不是一个无限增长的生词列表。

**(2) 吞吐调平**

| 场景 | 现在 | 改为 |
|---|---|---|
| 积压 ≤ 20 | 5 张 | 5 张（不变） |
| 积压 > 20 | 10 张 | **动态：min(10 + floor(积压/40), 20)** |
| 新词配额 | 固定 3 | **积压 > 100 时降到 1**，先消化存量 |

同时给**采集**加闸：单次交卷最多采集 5 个新词（现在无上限）。宁可漏收，不可淹没。

**(3) 采集质量**

现在只要答错就把正确答案里的生词收进来。加两条过滤：
- 已在「已掌握」状态的词不重复收
- 一次交卷内同一个词只收一次

### 5.3 与等级的关系

雅思轻量、O-Level 基础两层**建场即推送配套词表**（既有 `pushBasicWordlistForPaper` 机制，扩展到新层）。其余三层维持「答错自动采集」。

## 6. 错题本修复

### 6.1 诊断

871 条错题、0 条销账。规则是「做对 → streak=1；**隔天**再做对 → streak=2 → 自动销账」。

零销账说明：要么没人进重练页，要么进了但没有「隔天再来」。两者都指向**入口问题**——重练和词汇一样，不在任何必经路径上。

### 6.2 改动

1. **把错题重练挂进交卷后的仪式**：交卷 → 词汇自测 → **错题重练（有待练错题时，最多 3 题）** → 成绩页。与词汇自测同样的"寄生"策略。
2. `/my-mistakes` 顶部显示「待销账 N 条 · 今天可练 M 条」，让进度可见。
3. 销账规则**保持不变**（隔天两次做对）。规则本身是对的——它防的是「刚看完答案立刻再做一遍」的假掌握。先修入口，再看数据。

## 8. 度量与 A/B 设计

### 8.1 为什么不做随机对照

全校早测只有一个班 32 人。随机分半 → 每组 16 人，任何指标的置信区间都会大到无法判断；更重要的是**教学公平性**：不能让一半学生用已知更差的版本。

**替代方案：前后对比 + 分层观察 + 单向灰度。**

### 8.2 指标定义

| 模块 | 主指标 | 辅助指标 | 基线（2026-08-24） |
|---|---|---|---|
| 词汇 | **复习完成率** = 有复习动作学生数 / 有生词本学生数 | 人均复习次数、待开始占比 | 18/32 = 56%；人均 8.7；待开始 68% |
| 词汇 | **积压比** = 待开始 / 总词条 | — | 68%（目标 ≤ 40%） |
| 错题 | **销账率** = 已销账 / 总错题 | 进入重练页人次 | 0%（目标 ≥ 15%） |
| 等级适配 | **空题率** = 未作答题数 / 总题数 | 各层平均分、完成时长 | 待测（分层统计） |
| 内容 | **重复率** = 重复卷场次 / 总场次 | 各桶剩余篇数 | 雅思 100%（目标 0%） |

### 8.3 分层观察

新增两层后，按层拆分「空题率」和「平均分」。**判断标准**：

- 某层空题率 > 40% → 这层对该批学生仍然太难，需要下调或分流
- 某层平均分 > 85% → 太简单，学生该往上走一层
- 理想区间：空题率 < 15%，平均分 60–80%

这实际上是一个**分层是否合理**的持续检验，比一次性 A/B 更有价值。

### 8.4 单向灰度

新功能（词汇主页、错题重练入口）**先对 O-Level 基础层的学生开放**——他们最需要，且样本行为最容易观察。一周后无问题再全量。

灰度开关：`VOCAB_HOME_ROLLOUT = 'basic' | 'all' | 'off'`。

### 8.5 观察窗口

- 上线后第 3 天：看词汇复习完成率、错题重练进入人次（判断入口是否通）
- 上线后第 7 天：看积压比、销账率（判断吞吐是否改善）
- 上线后第 14 天：看分层空题率（判断等级划分是否合理）

## 9. 迁移与上线

### 9.1 数据库迁移

```sql
ALTER TYPE "EnglishLevel" ADD VALUE 'ielts_light';
ALTER TYPE "EnglishLevel" ADD VALUE 'olevel_intermediate';
```

Postgres 的 `ALTER TYPE ... ADD VALUE` **不能在事务块里跑**，Prisma migrate 默认包事务 → 迁移文件需要单独成文件且不含其他语句。

### 9.2 上线顺序

1. 迁移 + 注册表 + picker 分发（无用户可见变化）
2. 内容入库（雅思轻量 5 篇、雅思标准 6 篇）+ 审计
3. 给班级配置新等级（此时学生才看得到）
4. 词汇 / 错题改动（带灰度开关，默认 basic）
5. 出勤收尾（纯展示层）

### 9.3 回滚

| 改动 | 回滚方式 |
|---|---|
| 新等级 | 删掉班级的 `ClassEnglishLevel` 行即可，枚举值留着无害 |
| 词汇吞吐 | 常量改回，无数据迁移 |
| 错题入口 | 灰度开关设 `off` |
| 出勤展示 | `MORNING_QUIZ_ATTENDANCE_TRACKING=on` |

新增枚举值**不可回滚**（Postgres 不支持删枚举值），但留着不用无副作用。

## 10. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 五个等级 = 每天 5 场，考勤/判分工作量翻倍 | 老师负担 | 一个班不必开满 5 层；建议开 3 层（真题 / 标准 / 基础），另两层按需 |
| 自撰雅思被当成真题 | 学生误判难度、家长质疑 | `provenanceNote` 写明；与真题桶物理隔离；卷名前缀区分 |
| 词汇采集加闸后收得太少 | 生词本变空 | 闸设在 5 词/次，按现有数据（14 天 430 词 ÷ 约 60 人次 ≈ 7 词/次）只削峰不断流 |
| 错题重练插进交卷流程，拉长学生停留 | 学生不耐烦 | 上限 3 题；与词汇自测共用「没有就跳过」的规则 |
| 迁移加枚举值失败 | 上线受阻 | 单独迁移文件、不含事务；本地先验证语句 |

### 过程中发现的事实（值得记住）

**1. 兜底 cron 从来没跑过。** `MORNING_QUIZ_DAILY_FALLBACK` 在生产未设置，
而它的第一行就是「不等于 'true' 就 return」。这正是 2026-08-18 空场无人
救回的原因 —— 安全网写好了但开关没开。同类的还有
`MORNING_QUIZ_AUTO_GENERATE`（周日自动排课）。

**2. 手动改生产枚举要先部署代码。** 本次先在库里 `ALTER TYPE ADD VALUE`
加了两个等级值、又写了 ClassEnglishLevel 行，但代码还没部署 —— 这中间
旧代码遇到 `ielts_light` 会落进 else 分支抽成 O-Level 标准。正确顺序是
**先推代码、等部署完成，再动数据和开关**。

**3. Railway 的公网代理会间歇性断。** 入库过程中 `Can't reach database
server` 反复出现，TCP 可达但 Prisma 连不上；简单查询能过、NestFactory
起 app context 就失败。改成直接 `new PrismaClient()` + 直接实例化 service
