# 颁奖画面：用户确认效果图后的实现

2026-09-18。用户确认生成的手机效果图并要求照此实现。本轮只改展示，不改授奖、收藏、学习事实、获取门槛或数据库。

## 展示约定

- 覆盖整个网页可视区域，原 App 保留在暗色轻微模糊背景下；没有弹窗卡片或不透明模型方框。网页不控制系统状态栏。
- 原 V5 真实模型、浮雕和正背面保留。颁奖模型只做一次纵轴 360°，不播放原复杂开合编舞、不响应拖动；收藏详情保留原交互。
- 模型就绪后：0–0.3 秒停正面，0.3–1.9 秒转一圈，1.9 秒标题淡入，2.2 秒获得条件淡入，2.7–3 秒「继续」淡入。
- 16 枚各有简洁的获得条件；每日新词按任务份数计，不能误说成单词数；补做按原任务日期计。
- 10 个稀疏金色光点与柔和光晕，约 3 秒后收敛静止。没有循环闪烁和彩纸。
- 多枚：约 4.8 秒后自动下一枚，留出读文字时间。最后一枚永远等待学生点「继续」，不自动关闭。
- 任意时刻可跳过全部或按 Escape。延迟动作在关闭、路由变化、账号变化时清理；真实通知与纯展示预览继续互斥。
- **转完之后可以拖动**（2026-09-18 用户要求）：整圈结束前不响应手指，免得把动画打断；结束后画布交还给手指，学生能自己转着看正反面，画面下方给一行「用手指拖动徽章，可以转着看」。多枚排队时不给这行提示（马上要进下一枚）。
- 系统减少动态时不旋转、不播放光点；所有文字和操作仍可用。模型失败或 6 秒内未就绪（2026-09-18 起「就绪」含预热）则用原静态图继续展示；这不影响已保存的收藏。

## 验证边界

自动化覆盖阶段顺序、单次开始、同源且对应 iframe 消息校验、过期事件、降级、最后等待、四级独立队列、零预览写入、普通对话框回归。浏览器检查使用本机隔离假数据和真正 WebGL，不冒充真实学生任务；覆盖 320×568、390×844、844×390、1024×768 视口以及 16 枚模型各旋转位置。桌面浏览器视口检查不等同于已在实体 iPhone/iPad Safari 上测试。

生产发布不需要新增数据库迁移、密钥、付费接口或改动生产数据。

## 「卡一下就跳到最终画面」回归（2026-09-18）

用户在真机上看到：徽章先大大地停住，接着一卡，直接变成缩小并带文字的最终状态，整圈旋转没出现。三个原因，都已修：

1. **旋转按墙上时间推进。** 帧循环用 `(now - 开始时刻) / 1.6s` 算进度，主线程卡两秒，恢复后的第一帧算出来就 ≥1，整圈被直接跳过并当场收尾。改为按**每帧实际间隔**累计（沿用帧循环已有的 50 ms 上限）：卡顿只会让它变慢，不会跳过。同时加 `CEREMONY_MAX_SECONDS=4` 封顶，极慢设备上也不会没完没了。
2. **加载时先铺一张静态大图。** 图片按容器铺满，模型按自己的构图渲染，两者尺寸对不上，换过去就是一次突变。颁奖态下加载中不再显示静态图，只有降级（模型失败 / 只看图片）才显示。
3. **文字按固定时刻出现。** 标题 1.9 s、条件 2.2 s、继续 2.7 s 都从「模型就绪」起算，与旋转本身无关，卡顿时文字会抢在旋转前面。改为**收到「转完」消息后**再依次淡入（0 / +0.3 s / +0.8 s），队列自动进入下一枚改为转完后 2.9 s。等不到消息时 6 秒兜底照常往下走，不会卡死。

4. **第一帧才做着色器编译和贴图上传。** 改 1 之后旋转不再被跳过，这些活就变成肉眼可见的「第一帧停住很久」（用户真机复现）。现在在报「就绪」之前先 `renderer.compileAsync(scene, camera)` + 真画一帧 + 等两帧，把这些活做完；预热失败也照常播，不因此不给徽章。相应地，颁奖态的就绪超时由 4 秒放宽到 6 秒（预热算在内），加载中不再是空屏，而是一行「正在呈现三维细节」。

5. **画面帧根本不来。** 改 4 之后又变成「提示出来了、徽章不转」：这个三维画面是内嵌 iframe，窗口被遮挡、系统省电或浏览器把它判为不可见时，动画帧会被节流到每秒两三帧甚至一帧不给（本机隔离环境实测：外层每秒 146 帧，iframe 内每秒 2 帧）。帧里的兜底同样推不动，所以加了两层：连续四帧间隔都 ≥50ms 就改按时间推进；再加一个 120ms 的定时器看门狗，发现帧断了就直接按时间推画面并照常收尾（定时器不受可见性节流）。降级成静态图时，图片也用 CSS 翻转一圈，学生不会看到一张僵住的图。

6. **预热压在「就绪」前面，手机上直接超时。** 同步编译着色器在 iPhone 上要好几秒，卡在报「就绪」之前 → 学生只看到「正在呈现三维细节」，6 秒后超时直接跳到最终画面（用户真机截图）。改成**先报就绪让徽章露面，再预热，预热完再报 `warm`**；外层收到 `warm` 后 0.3 秒开转，等不到 `warm` 则 2.5 秒后照常开转。这也是顺序上的定论：**任何耗时的准备都不许排在「就绪」前面。**

7. **真机诊断（2026-09-18，老师测试号截图）**：ready 1.9s · warm 2.0s · 发开转 2.3s · complete 3.9s —— 动画本身是对的（截图里徽章明显转到一半），剩下的是**开头 1.9 秒空等**：模型一两兆，点开颁奖才开始下载。改为提前预取：老师预览里选中哪一枚就先拉，学生端在通知队列里知道下一枚时先拉（`prefetchMedalModel`，只碰 `/medals/v5/models/` 静态文件、不带身份；契约测试「不得绕过 request() 裸 fetch」为它开了一个钉死在该路径上的例外）。

**教训**：连改四轮都在按症状猜，每次只猜中一层。第五轮先在老师预览里加了一行逐步诊断（ready / warm / 发开转 / complete + 秒数，学生看不到），一张截图就定位完毕。**以后这类只在真机上出现的问题，先上诊断再改代码。**

另外：整圈结束时若页面正好在后台，`complete` 发不出去，回到前台会补发一次（只发一次），否则外层会一直等。

自动化覆盖：卡顿 2 秒后仍能转过背面与侧面并正常收尾、8 fps 下 4 秒内收尾、后台完成后回前台补发、文字必须等转完、6 秒兜底。浏览器实测用本机静态服务播放真实 WebGL 模型，逐帧截图确认转过侧面与背面并回到正面。桌面检查不等同于实体 iPhone/iPad Safari 实测。

## 深色模式透明背景回归

首次发布后用户 iPhone 截图出现白色矩形并遮标题。已在桌面 Chromium 的深色模式精确复现，不应归咎于 iPhone 本身。原因：外层 iframe 继承 App 的 dark 色彩模式，内层 root 默认 light；[CSS Color Adjustment §2.2](https://www.w3.org/TR/css-color-adjust-1/#color-scheme-effect) 要求这种不一致的嵌入文档使用不透明 Canvas，即使 CSS 背景和 WebGL 都透明。

修复仅把颁奖 iframe 及其内层 root 显式匹配为 light，保持实际背景透明；不改变 App 深浅偏好、徽章配色或普通收藏详情。标题另设独立层级，避免被模型容器遮挡。回归必须在系统深色和 App 手动深色模式检查真实截图；只断言 background 为 transparent 不足以发现这类问题。
